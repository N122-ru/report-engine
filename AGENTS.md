# DOX framework

- DOX is highly performant AGENTS.md hierarchy installed here
- Agent must follow DOX instructions across any edits

## Core Contract

- AGENTS.md files are binding work contracts for their subtrees
- Work products, source materials, instructions, records, assets, and durable docs must stay understandable from the nearest applicable AGENTS.md plus every parent AGENTS.md above it

## Read Before Editing

1. Read the root AGENTS.md
2. Identify every file or folder you expect to touch
3. Walk from the repository root to each target path
4. Read every AGENTS.md found along each route
5. If a parent AGENTS.md lists a child AGENTS.md whose scope contains the path, read that child and continue from there
6. Use the nearest AGENTS.md as the local contract and parent docs for repo-wide rules
7. If docs conflict, the closer doc controls local work details, but no child doc may weaken DOX

Do not rely on memory. Re-read the applicable DOX chain in the current session before editing.

## Update After Editing

Every meaningful change requires a DOX pass before the task is done.

Update the closest owning AGENTS.md when a change affects:

- purpose, scope, ownership, or responsibilities
- durable structure, contracts, workflows, or operating rules
- required inputs, outputs, permissions, constraints, side effects, or artifacts
- user preferences about behavior, communication, process, organization, or quality
- AGENTS.md creation, deletion, move, rename, or index contents

Update parent docs when parent-level structure, ownership, workflow, or child index changes. Update child docs when parent changes alter local rules. Remove stale or contradictory text immediately. Small edits that do not change behavior or contracts may leave docs unchanged, but the DOX pass still must happen.

## Hierarchy

- Root AGENTS.md is the DOX rail: project-wide instructions, global preferences, durable workflow rules, and the top-level Child DOX Index
- Child AGENTS.md files own domain-specific instructions and their own Child DOX Index
- Each parent explains what its direct children cover and what stays owned by the parent
- The closer a doc is to the work, the more specific and practical it must be

## Child Doc Shape

- Create a child AGENTS.md when a folder becomes a durable boundary with its own purpose, rules, responsibilities, workflow, materials, or quality standards
- Work Guidance must reflect the current standards of the project or user instructions; if there are no specific standards or instructions yet, leave it empty
- Verification must reflect an existing check; if no verification framework exists yet, leave it empty and update it when one exists

Default section order:
- Purpose
- Ownership
- Local Contracts
- Work Guidance
- Verification
- Child DOX Index

## Style

- Keep docs concise, current, and operational
- Document stable contracts, not diary entries
- Put broad rules in parent docs and concrete details in child docs
- Prefer direct bullets with explicit names
- Do not duplicate rules across many files unless each scope needs a local version
- Delete stale notes instead of explaining history
- Trim obvious statements, repeated rules, misplaced detail, and warnings for risks that no longer exist

## Closeout

1. Re-check changed paths against the DOX chain
2. Update nearest owning docs and any affected parents or children
3. Refresh every affected Child DOX Index
4. Remove stale or contradictory text
5. Run existing verification when relevant
6. Report any docs intentionally left unchanged and why

## User Preferences

When the user requests a durable behavior change, record it here or in the relevant child AGENTS.md.

- Preserve the SamGTU branding: bundled `default_logo.png` assets, the MetadataForm label, and historical journal mentions. Use fictional institutions and people in test fixtures instead of real identities.

## Child DOX Index

- `backend/AGENTS.md` — backend API, document generation, validation, sessions, MCP, and backend runtime assets.
- `frontend/AGENTS.md` — React/TypeScript application, UI components, browser services, and static frontend assets.
- `assets/AGENTS.md` — shared runtime assets and the canonical report-agent instruction file.
- `tests/AGENTS.md` — backend/API/document-generation regression tests.
- `.github/AGENTS.md` — CI quality gates, native release workflows, and maintainer publication contracts.
- `release_tools/AGENTS.md` — versioned native package assembly, launchers, and the maintainer build/release guide.

# AGENTS.md — Журнал поведения моделей и гайд для разработчиков

Документ предназначен для разработчиков и ИИ-ассистентов, развивающих и поддерживающих проект **Lab-Constructor (Report Engine)**.

---

## 1. Архитектура и суть проекта

* **Назначение:** Web-генератор и валидатор нормоконтроля студенческих отчётов по ГОСТ 7.32-2017 и ГОСТ 2.105-2019 (название вуза, институт и кафедра — пользовательские плейсхолдеры).
* **Стек:**
  * **Backend:** FastAPI (Python 3.13), `python-docx` + прямое низкоуровневое XML-манипулирование (`oxml_utils.py`), опциональный локальный PDF-конвертер, Mammoth, Pytest.
  * **Frontend:** React 19, TypeScript, Tailwind CSS, Vite, Lucide Icons, KaTeX (предпросмотр формул).
* **Рабочий процесс генерации отчёта:**
  1. Пользователь загружает скриншоты/код в окно «Промпты для нейросетей» (`AiPromptModal`).
  2. Выбирает тон изложения (`student` / `academic` / `concise`), лицо повествования, формулы LaTeX и флаг блоков кода.
  3. Копирует сгенерированный системный промпт в внешнюю LLM (Gemini / Claude / ChatGPT).
  4. Вставляет ответ во вкладку «Вставить ответ нейросети». Функция `cleanAiResponse` нормализует Markdown.
  5. В редакторе работает предпросмотр страниц А4, автоисправление типографики и скачивание DOCX; PDF доступен при наличии локального конвертера.

## 2. Журнал поведения LLM (Edge Cases & Паттерны)

### 2.1. Конфликт жестких ограничений (Constraint Over-Triggering)
* **Симптом:** Пользователь дал скриншот адаптеров сети, методичка требует «определить назначение адаптеров», но модель выдала только сухой статус: `Адаптер X: среда передачи недоступна`.
* **Причина:** В промпте стоял чрезмерно агрессивный негативный запрет:
  *«ПОЛНЫЙ ЗАПРЕТ НА ОПРЕДЕЛЕНИЯ: никаких фраз вида "... — виртуальный интерфейс прямого сопряжения..."»*.
  LLM штрафует негативные правила сильнее позитивных, поэтому модель запаниковала и выкинула нужное описание назначения, чтобы случайно не нарушить запрет на определения.
* **Решение:**
  * **Промпт должен быть универсальным**, без упоминания конкретных устройств и узких запретов.
  * Введено правило **«Принцип инженерной конкретики»**:
    * ✔ *Назначение элементов в контексте работы:* РАЗРЕШЕНО и ОБЯЗАТЕЛЬНО (1 лаконичной строкой: зачем элемент нужен на стенде/в программе).
    * ✖ *Энциклопедизм из Википедии:* ЗАПРЕЩЕНО (не писать историю стандартов, общую теорию радиоволн и устройство ОС).

---

### 2.2. Ложные блоки кода ````text ```` вокруг расчетов
* **Симптом:** Модель оборачивает математические формулы, списки октетов и перевод систем счисления в ````text ... ````, ломая верстку отчета.
* **Причина:** Модели обучены оформлять моноширинный вывод терминала в ````text````.
* **Решение:**
  * В промптах зафиксировано: «КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО создавать блоки ````text ```` для расчетов, формул и списков».
  * Добавлен переключатель «Блоки текста / кода» (по умолчанию выключен).
  * В `cleanAiResponse` и бэкенде встроен авто-распаковщик: если блок ````text ```` содержит математику (`$`), двоичные цепочки или списки, он автоматически распаковывается в чистый Markdown.

---

### 2.3. Поисковые сноски и маркеры (Search Grounding Clutter)
* **Симптом:** Модели с включенным веб-поиском (Gemini, Copilot, Perplexity) вставляют в текст `[cite: 4]`, `[cite: 1, 2]`, `【1†source】`, `[^1^]`.
* **Решение:**
  * Прямой запрет в промпте: «КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО вставлять цитаты, сноски и маркеры поисковых систем».
  * Автоматическая зачистка регулярками в `cleanAiResponse` и `autofix` с устранением повисших пробелов перед знаками препинания (`"команда ."` $\to$ `"команда."`).

---

### 2.4. Словесный мусор и псевдонаучный канцелярит
* **Симптом:** Модель пытается искусственно раздуть объем академическими фразами:
  *«В рамках проведения комплексного декомпозиционного анализа архитектуры...»*,
  *«Следует отметить, что...»*,
  *«находится в активном состоянии и обеспечивает...»*.
* **Решение:**
  * В `cleanAiResponse` и `autofix`:
    * `В рамках проведения комплексного анализа...` $\to$ `В ходе анализа`
    * `Следует отметить, что...` $\to$ удаляется
    * `находится в активном состоянии` $\to$ `активен`

---

### 2.5. Дублирование подписей к рисункам
* **Симптом:** Модель оформляет картинку `![Название](url)` и следом отдельной строкой пишет `Рисунок 1 — Название`.
* **Причина:** Конвертер сам формирует ГОСТ-подпись «Рисунок N — ...» из `alt`-текста в скобках `![alt]`. Повторная строка создает визуальный дубль.
* **Решение:**
  * В промпте: запрет дублировать подпись отдельной строкой.
  * В бэкенде и фронтенде: регулярное выражение находит и поглощает текстовые строки `Рисунок N — ...` до и после картинки, перенося осмысленный текст внутрь `![...]`.

---

### 2.6. Лицо изложения (ГОСТ 7.32-2017 п. 6.1.4)
* **Симптом:** Модели по умолчанию скатываются в «Я настроил» или «Мы исследовали».
* **Правило:** По ГОСТ 7.32 текст отчета обязан быть в безличной форме («выполнено», «настроено», «рассчитано», «исследовано»).
* **Важное инженерное решение:** Нельзя делать автозамену местоимений регулярными выражениями («я выполнил» $\to$ «выполнено»), так как в русском языке ломаются окончания зависимых слов и падежи. Стиль задается ролевой инструкцией в промпте.

---

### 2.7. Гиперфиксация на таблицах
* **Симптом:** Модель упаковывает ход работы в таблицу «Шаг | Действие | Результат» или делает таблицы со сложными формулами внутри ячеек.
* **Правило ГОСТ:** Таблицы применяются только для сводных числовых показателей и матриц измерений. Формулы оформляются выключными строками (`$$...$$`).
* **Решение:** Явный запрет в промптах на таблицы для формул и для пошагового описания хода работы.

### 2.8. Устранение вариативности тона и лица изложения
* **Решение:** Выбор «душноты» и грамматического лица удален из интерфейса как избыточный. По ГОСТ 7.32-2017 п. 6.1.4 отчёт обязан быть строго обезличенным («выполнено», «настроено», «исследовано»). Тон зафиксирован в виде практического языка студента-инженера (техническая конкретика, 1 строка контекста на элемент, без Википедии и псевдонаучной воды).

---

### 2.9. Режим «Т9» (подсветка ошибок, без автокоррекции)
* **Проблема:** Студенты копируют в промпт небрежные логи, быстрые заметки или голосовой ввод с опечатками.
* **Решение:** Т9 — это только подсветка возможных ошибок в редакторе (`spellCheck`), без молчаливого исправления текста. Блок «Режим Т9» удалён из всех ИИ-промптов: модель не нормализует черновики, сомнительные места помечает явно, числовые параметры, IP-адреса, хеши и идентификаторы не трогает никогда (см. `SKILL.md`). Тумблер «Т9» на панели редактора включает проверку орфографии браузера.

---

### 2.10. MCP-сервер Report Engine (только live SSE, без stdio)
* **Проблема:** Постоянное копирование текста между вкладками утомляет; при запросе к LLM «исправь пункт 2» модель переписывает весь 10-страничный Markdown с нуля, галлюцинируя и теряя формулы или скриншоты.
* **Решение:**
  * Агент работает через live SSE-сессию (`/api/mcp/sse?token=...`) прямо с открытой вкладкой браузера. Отдельный stdio-сервер удалён как ненужный.
  * Инструменты агента: `list_images`, `get_image`, `upload_image` (медиа), `get_report_state`, `append_or_update_section`, `update_meta` (реквизиты титульника), `delete_image`, `lint_report`, `autofix_typography`.
  * Удалены как мёртвые/вредные: `get_templates` (пустые нейтральные строки), `inspect_report_structure` (дубль линтера), `compile_docx` (писать на диск сервера противоречит Zero Disk Wear), `set_full_report` (провоцирует полную перезапись).
  * Единый источник инструкций агента — `assets/SKILL.md`: сервер отдаёт его через ресурсы/промпты MCP (`report://rules/gost732`).

### 2.11. Инструкция для агента в 1 клик (UX без ручного редактирования JSON)
* **Проблема:** Студенты не умеют или не хотят вручную находить скрытые файлы конфигураций (`mcp_config.json`, `.cursor/mcp.json`), редактировать JSON и перезагружать IDE.
* **Решение:** В окне «ИИ-агент (MCP)» добавлен режим «Инструкция для ИИ (в 1 клик)». Пользователь копирует одну готовую инструкцию и просто отправляет её в чат своему ИИ-агенту (Antigravity, Cursor Agent, Cline, Claude Code). Агент сам подключает SSE-сервер, вызывает `get_report_state` и ведёт отчёт по ГОСТ 7.32.
* **Урок из скилла `report-live-gost`:** агент без явного указания пишет скилл по описаниям тулов и теряет правила (структуру, таблицы, «И.О. Фамилия», библиографию). Поэтому инструкция требует: прочитать `report://rules/gost732` и вписать без сокращений, помнить про протухание токена.

### 2.12. Мультимодальное зрение ИИ-агента через MCP (Vision & Live Media Sync)
* **Проблема:** Обычные текстовые модели галлюцинируют параметры со стенда (случайные пинги, выдуманные IP, фальшивые выводы консоли), из-за чего студент получает незачёт за несоответствие текста прикрепленным скриншотам.
* **Решение:**
  * Реализована сквозная мультимодальная синхронизация медиа:
    * Браузер автоматически загружает скриншоты в сессию (`POST /api/session/{token}/images`).
    * В MCP добавлены инструменты `list_images`, `get_image` (возвращает нативный MCP блок `{"type": "image", "data": base64, "mimeType": "..."}`) и `upload_image`.
    * Мультимодальные модели (Claude 3.5 Sonnet, GPT-4o, Gemini 2.0) получают скриншот прямо в контекст зрения и считывают фактические числа и дампы с экрана без галлюцинаций.
### 2.13. Чистый In-Memory бэкенд (Zero Disk Wear)
* **Проблема:** Постоянные промежуточные сохранения текста и скриншотов изнашивают SSD/флеш-память сервера при активной работе ИИ-агента и браузера.
* **Текущее состояние:** Текст и реквизиты сохраняются в `localStorage`, оригиналы изображений и манифест (имя, размер, SHA-256) — в IndexedDB браузера. Бэкенд хранит вложения и отметки об удалённых файлах только в RAM (`SessionData.images`, `SessionData.deleted_images`); при наличии локального конвертера конвертация DOCX в PDF использует удаляемые временные файлы.
* При открытии вкладки и переподключении SSE браузер сверяет хеши, копирует недостающие файлы в RAM сессии и забирает новые рисунки агента в IndexedDB. Разные байты под одним именем не заменяются молча. Отметки об удалении живут только до перезапуска сервера; восстановительная загрузка проверяет их повторно, чтобы не отменить удаление в гонке запросов.
* **Ограничение для развития:** Не вводить постоянное хранение отчётов, оригиналов изображений или истории правок на сервере. Если вкладка закрыта и RAM-сессия утрачена, агент не может читать вложения до следующего открытия браузера. Очистка хранилища браузера при утраченной RAM-сессии невосстановима без пользовательской копии; IndexedDB не заменяет резервный экспорт проекта.

### 2.14. Бригада соавторов и адаптивный титульный лист по ГОСТ
* **Решение:**
  * Добавлено динамическое управление составом бригады (несколько студентов) прямо во вкладке «Предмет и кафедра» с автоподстановкой группы и адаптивным расчетом таблицы подписей («Студенты» / «Студент»).
  * В живом предпросмотре А4 (`DocumentPreview.tsx`) реализована полная синхронизация с генератором DOCX: при выборе «Без логотипа» (`logo_mode === "none"`) плавающий блок логотипа скрывается, левый отступ убирается, а наименование университета форматируется по ГОСТ 2.105.
  * Для быстрого выбора академических должностей проверяющих («доцент», «ст. преп.», «ассистент», «профессор», «зав. кафедрой», «преподаватель») используется select со справочником и полем свободного ввода.

### 2.15. Пользовательские шаблоны дисциплин и нейтральность вуза
* **Проблема:** Захардкоженные дисциплины («Информационная безопасность», «Сетевые технологии», «Программирование и алгоритмы») и жесткая привязка к СамГТУ мешали студентам других вузов и специальностей, а ненужные шаблоны нельзя было удалить.
* **Решение:**
  * Список предустановленных предметов очищен (`DEFAULT_SUBJECT_PRESETS = []`). Пользователь создаёт только нужные ему предметы.
  * Добавлена возможность полного удаления шаблонов дисциплин (`deleteSubjectPreset`) как из верхней панели приложения, так и из вкладки «Предмет и кафедра».
### 2.16. Чистая доставка фронтенда в Docker (Zero Node on Prod)
* **Проблема:** Multi-stage сборка с `RUN npm ci` в Dockerfile требует наличия всех исходников фронтенда, `package.json` и `package-lock.json` на продакшн-сервере, что вызывало сбой сборки при переносе только готового бандла.
* **Решение:** Из `Dockerfile` полностью удалена стадия Node.js / `npm ci`. Образ собирается на базе Python 3.11-slim и напрямую копирует готовый `frontend/dist/`. В `.dockerignore` исключение `frontend/dist/` снято. На сервере деплоя больше не требуются Node.js, npm и исходный код фронтенда.
* **Обновление (проверено 2026-10-15):** сборка SPA снова вынесена в Dockerfile отдельной builder-стадией `node:22-slim` + `npm ci`, а `frontend/dist/` снова исключён в `.dockerignore`. Урок Zero Node on Prod сохраняется: Node нужен только на этапе сборки образа, в runtime-слое и на сервере деплоя — нет.

### 2.17. Устранение пафоса, капслока и маркетинговой лексики (Engineering Tone & Clarity)
* **Проблема:** Эмоциональные крики капслоком («КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО», «СТРОГИЙ ЗАПРЕТ», «АНТИ-ГИПЕРФИКСАЦИЯ»), сленг («причесать черновик», «без душноты», «снимет забор») и маркетинговые слоганы («HERO», «Live Sync», «Тебе больше не нужно...!») засоряли интерфейс и промпты.
* **Решение:**
  * Все системные промпты и правила переведены на выдержанный нормативно-инженерный язык без капслока и восклицаний.
  * В модальных окнах, кнопках тулбара и всплывающих подсказках удалены эмодзи-искры (`✨`) и театральные анимации (`animate-bounce`), заменены на плавные `fade-in`.
  * В MCP-манифестах и роутере убраны рекламные формулировки («МГНОВЕННО», «ГЛАВНЫЙ ИНСТРУМЕНТ», «без галлюцинаций», «на 100 баллов»), описания приведены к лаконичным техническим спецификациям.

### 2.18. Универсальность видов учебных и научных работ (не только лабораторные)
* **Проблема:** Захардкоженные упоминания «лабораторная работа» / «ЛР №» ограничивали использование сервиса для практических занятий (ПР), расчетно-графических работ (РГР), курсовых работ (КР) и проектов (КП), научных работ (НИР), отчетов по практике (производственная, учебная, преддипломная) и контрольных работ.
* **Решение:**
  * **Форма метаданных (`MetadataForm.tsx`):** Расширен список стандартных видов работ и добавлено текстовое поле свободного ввода для пользовательских видов работ.
  * **Панель инструментов и имена файлов (`App.tsx`):** Реализован динамический бейдж (`workTypeShort`) и префиксы скачиваемых файлов (`ЛР`, `ПР`, `РГР`, `КП`, `КР`, `НИР`, `ПП`, `УП`, `ПДП`, `КСР`, `Работа`).
  * **Генерация промптов ИИ (`AiPromptModal.tsx`, `SKILL.md`, `mcp_router.py`):** Реализовано корректное грамматическое склонение вида работы («о лабораторной работе №1», «о практической работе №2», «по курсовому проекту», «по производственной практике»), а итоговые выводы обобщены («В ходе выполнения работы исследованы...»).
  * **Титульный лист (`title_page.py`, `DocumentPreview.tsx`):** Номер работы подставляется опционально (для курсовых и практик без номера не выводится лишнее «№0»).

### 2.19. SKILL.md как единый источник инструкций агента
* **Проблема:** Правила ГОСТ были пересказаны 4 раза (модалка, stdio-сервер, 2 места в SSE-роутере) и разъехались: запреты сносок, дублей подписей и `text`-блоков терялись в MCP-версиях.
* **Решение:** Канонические инструкции живут в `assets/SKILL.md` (едет в Docker-образ вместе с остальными ассетами). SSE-сервер отдаёт его текст через ресурсы (`report://rules/gost732`) и `prompts/get`, инструкция подключения предлагает агенту сохранить workflow как skill в своей среде.

### 2.20. Чистка модалки промптов от дублей
* Статус-строки `📸/💻/🏛️` дублировали состояние чекбоксов и нарушали запрет эмодзи (2.17) — удалены вместе с блоком «Режим Т9».
* Правило: подписи в хроме модалок не дублируют очевидное («ГОСТ такой-то» в футерах), ссылки на пункты ГОСТ живут только внутри правил, где они load-bearing.

### 2.21. Автоподсказка следующего номера работы
* В шаблоне предмета хранится `last_work_number` (обновляется при правке номера, командах агента и скачивании). При выборе шаблона номер подставляется как `last+1`.
* Автоподстановка при переключении счётчик не двигает (skip-флаг), иначе было бы самонакручивание 5→6→7.
* Агент номер берёт из методички/скринов, фолбэк — подсказанное значение из `get_report_state` (см. `SKILL.md`).

### 2.22. Конструктор списка литературы (ГОСТ Р 7.0.5)
* Источники хранятся в `meta.references` (вид book/article/website/standard), форматирует `bibliography.py`, раздел «СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ» рендерится последним в DOCX и превью. Агент заполняет через `update_meta`.
* В DOCX строки помечены стилем `Bibliography`, линтер их пропускает (иначе «1. ...» с точкой сочлось бы заголовком). Линтер требует ссылок `[1]` в тексте при наличии списка — это же правило вшито в `SKILL.md`.
* Зеркало форматтера для превью — `frontend/src/services/bibliography.ts`: править оба файла одинаково. Паритет проверяется побайтово (TS собирается через tsc в /tmp, сравнение с Python по тем же кейсам).
* Зеркало типографики — `frontend/src/services/typography.ts` (порт `apply_typography_rules`; границы через юникодный класс — JS `\b` не дружит с кириллицей). Строки источников типографируются с обеих сторон одинаково.
* Источники идут общими блоками пагинации (`bibhead`/`bibref`), шапка раздела — с новой страницы как `pageBreakBefore` в DOCX. Оценка объёма считает слова источников с обеих сторон.

### 2.23. Русская морфология ломает regex-детект разделов
* Проверка структуры (Цель/Ход/Вывод) дважды падала на мелочах: сначала `цели?` (нет мягкого знака — совпадает только «цели», но не «цель»), потом `цель(?:и)?` («цели» — это цел+и, мягкого знака там нет вообще). Правильно: `^цел(?:ь|и)`, для вывода `^вывод(?:ы|ов)?`.
* Урок: русские флексии — не суффиксы, regex-опциональность к ним неприменима. Паттерны детекта одинаковые с обеих сторон (без `\b` — см. 2.22), plural-варианты (`Выводы`, `Цели`) считаются найденными, иначе студенты огребут за каноничное именование.

### 2.24. Ручная нумерация рисунков/таблиц и предупреждение о неприкреплённых изображениях
* Номер автора хранится строкой verbatim (`4.2`, `4.3`, `4.1` в любом порядке) во всех трёх местах: `markdown_parser.py`, `linter.py`, `DocumentPreview.tsx`. Автонумерация — только fallback для подписей без номера. В линтере номер экранируется через `re.escape`/`escapeRegExp` (точка в `4.2` иначе матчит любой символ).
* Неприкреплённые изображения: бэкенд вставляет плейсхолдер `[ Иллюстрация: ... ]`, линтер даёт `WARNING IMAGES`, превью — предупреждение в нормоконтроле, а скачивание DOCX/PDF спрашивает подтверждение со списком недостающих файлов. Код в заборах и внешние URL (`http/data:/blob:`) недостачей не считаются. Хелперы: `find_missing_images` (backend), `findMissingImageRefs` (`App.tsx`).

### 2.25. Версионирование правок и размещение рисунков
* `revision`/`meta_revision` вычисляются из содержимого сессии; браузер и MCP отправляют ожидаемую версию. Сервер отклоняет запоздалую запись (409), а UI сохраняет локальный черновик и показывает оба варианта для выбора. Писать поверх конфликта без явного решения нельзя.
* Границы разделов и блоков определяются по Markdown-токенам, не регуляркой по строкам. ID в `get_document_outline` привязаны к версии: после каждой правки их нужно получить заново. `get_last_edit`, `get_edit_history`, `rollback_last_edit` работают с последними 20 снимками в RAM без перезаписи соседних разделов.
* Размещение рисунка хранится в `meta.image_layouts` по имени файла, а не в alt-тексте. Его редактируют MCP `update_image_layout` или шторка иллюстраций; DOCX и предпросмотр используют одни параметры ширины, высоты, выравнивания и переноса страницы. Предпросмотр остаётся оценочным — фактическую пагинацию подтверждают в DOCX/PDF.
* Несколько текстовых исправлений выполняются одной версионированной операцией `apply_patches`; `upload_images` предварительно проверяет все файлы и якоря, затем добавляет пакет в сессию. Названия с кириллицей сохраняются, пробелы нормализуются, а сопоставление ссылки и параметров размещения допускает нормализованное имя.

### 2.26. Защита записывающих MCP-команд и оригиналов изображений
* Все записи MCP требуют свежую версию соответствующей части отчёта: `revision` для текста, изображений и типографики, `meta_revision` для реквизитов и размещения. Инструкция без проверки версии не заменяет проверку на сервере.
* `rollback_last_edit` откатывает только последнюю правку агента, не правку студента. Автотипографика пропускает блоки кода и абзацы с Markdown-ссылками, чтобы не испортить буквальные пути к изображениям; результат содержит diff.
* Загрузка не заменяет файл с уже существующим нормализованным именем и отклоняет пустые данные. Браузерный пакет файлов сначала проверяется целиком, затем сохраняется; UI показывает ошибку передачи и позволяет повторить её без потери локального `File`. `delete_image` не удаляет файл, пока на него ссылается Markdown.
* Синхронизация браузера передаёт временный `client_id` вкладки; собственное SSE-подтверждение не считается удалённым конфликтом. Изменения другой вкладки или MCP по-прежнему требуют разрешения через UI.

### 2.27. Повторные события реквизитов, литералы и титульник
* `update_meta` не отправляет SSE при неизменном содержимом. Браузер сравнивает реквизиты через канонический JSON с отсортированными ключами на всех уровнях; порядок студентов и источников в массивах сохраняется. Изменение `image_layouts` обозначается как размещение рисунков, а не правка титульника.
* Инлайн-разбор предпросмотра использует `markdown-it`, как DOCX использует `markdown-it-py`: экранированные звёздочки, вложенное жирное/курсивное начертание и парные backtick-разделители любой длины больше не разбираются отдельной регуляркой. Ячейки DOCX-таблиц проходят тот же разбор инлайн-токенов, что абзацы.
* Технические кавычки и операторы сохраняются внутри инлайн-кода, который выводится обычным Times New Roman. Обёртки любой длины защищаются от автофикса через CommonMark-парсер; обычный апостроф `'` не является разделителем кода. Последовательность `\\n` не превращается в перевод строки повторно: JSON декодируется один раз.
* Перетаскивание файлов принимается всей шторкой медиа и полем редактора. Для пустого или общего MIME-типа используется известное расширение изображения; дубли нормализованных серверных имён отсекаются до загрузки. Сортировка по умолчанию естественная по имени (2 перед 10), доступны обратная и по размеру; предпочтение хранится только в браузере.
* Шапка титульника — обычное начертание 12 pt, без принудительного капслока и разрядки в предпросмотре. В DOCX красная строка шапки сбрасывается явно даже без логотипа. Предпросмотр использует те же интервалы и смещения логотипа, что генератор; жирное начертание сохраняется для названия документа и темы.

### 2.28. Сохранение шаблона, пустой нормоконтроль и вставка таблиц
* Обновление активного шаблона дисциплины не вызывает повторный выбор предмета и не повышает номер текущей работы. Подсказка `last_work_number + 1` сохраняется при настоящем переключении шаблона.
* Пустой или состоящий из пробелов Markdown показывает «Нет текста для проверки» и нейтральный бейдж «Нет текста» вместо оценки и «Готово». Одни `meta.references` не считаются телом отчёта; оценки непустого текста рассчитываются по прежним правилам.
* Таблица вставляется через `onRegisterInsert` на текущую позицию курсора и заменяет выделение, после чего textarea получает фокус с курсором за таблицей. Последнее выделение хранится в `App` на время переходов к форме; регистрация сбрасывается при размонтировании, отложенная вставка выполняется после нового монтирования по актуальному тексту. Разделительный перевод строки перед подписью сохранён. Форматирование и вставка рисунков сохраняют прежнее поведение выделения.
* Проверены переходы пустой → непустой → пустой текст, источники без тела, сохранение и переключение шаблонов, изменение выделения при открытой модалке, обновление текста сессией при размонтированном редакторе и возврат фокуса на desktop 1440 px и mobile 390 px.

### 2.29. `file_path` — только автономные сборки, вместо скрытой переменной окружения
* **Проблема:** доступ к файлам на машине сервера в live включался переменной `REPORT_ENGINE_MCP_FILE_ROOT`, объявленной только в backend-доках и тестах. Схемы инструментов всегда рекламировали `file_path`, вызов без переменной падал с «Файловые источники отключены», и пользователь нигде не мог понять, что происходит.
* **Решение:** политика стала режимом запуска, а не настройкой. Флаг живёт в `backend/app/engine/local_files.py`: headless читает пути всегда, переносимый web включает его в `standalone_web.create_application` (процесс на машине пользователя), Docker и веб из исходников остаются base64-only. В сетевых сборках `tools/list` вовсе не показывает `file_path` (схемы изображений требуют `base64_data`, профиль — объект `profile`), а вызов получает ошибку с готовой альтернативой. `get_capabilities.file_path` отдаёт `"standalone"` или `false`; переменная окружения удалена.
* **Принцип:** пользователь автономной сборки ничего не настраивает и не знает про пути — за него решает режим запуска; агент узнаёт политику из `get_capabilities` и схем, а не из доков.

### 2.30. Синхронизация команды подключения и инструкций агента с кодом
* **Проблема:** аудит live/headless MCP нашёл расхождения: конфиг Claude Code без `"type": "sse"` клиент читает как stdio и пропускает сервер; команда «в 1 клик» не требовала читать все страницы `tools/list` и не объясняла привязку к открытой вкладке; `SKILL.md` содержал англоязычный абзац внутри русского ядра и формулировки строже реального контракта; чеклист `agent_onboarding` не упоминал `tools/list`; лаунчеры называли устаревшие версии Python/Node.
* **Решение:**
  * Конфиг Claude Code получает `"type": "sse"`; команда и `SKILL.md` требуют `get_capabilities` и все страницы `tools/list` (nextCursor) и прямо называют симптом устаревшей ссылки: пустой отчёт или молчащие инструменты → попросить свежий URL в окне «ИИ-агент (MCP)». Плашка модалки переименована в «Токен готов» с пояснением про открытую вкладку.
  * Зеркало контракта в `SKILL.md`: `expected_snapshot_id` для `upload_images` на обоих транспортах, гейт `lint_report(markdown_content)` (альтернативный текст не открывает экспорт), указатели на `update_image_layout`/`delete_images` и `tools_diff`, имена точечных редакторов; англоязычный абзац о `$N` переведён на русский. Описание `markdown_content` в схеме `lint_report` дополнено тем же правилом, пункт 3 чеклиста onboarding читает все страницы `tools/list`.
  * Сообщения `start.sh`/`start.py` приведены к фактическим требованиям (Python 3.11+, Node 20.19+/22.12+); в README добавлена строка про macOS.

## 3. Правила для агентов и разработчиков

1. **Универсальность промптов:**
   Никогда не зашивайте в системные промпты правила под одну конкретную дисциплину (например, запреты конкретно про сетевые адаптеры). Промпты должны одинаково надежно работать для сетей, Python, схемотехники, баз данных и физики.
2. **Индивидуальные требования преподавателя:**
   Для специфических условий конкретной работы используйте поле `custom_instructions` (сохраняется в шаблоне отчёта) — оно имеет наивысший приоритет в промптах.
3. **Не плодить лишний код:**
   Все идеи, инсайты по поведению моделей и заметки фиксировать прямо в этом файле `AGENTS.md`. Не создавать вспомогательные dev-эндпоинты или тяжелые структуры логов, если в них нет прямой необходимости.
4. **Формат ФИО в UI (строго):**
   Во всех пользовательских подписях, плейсхолдерах и описаниях API использовать только `И.О. Фамилия` (ГОСТ 7.32 / ГОСТ Р 7.0.97). Слово `ФИО` в UI запрещено — оно противоречит требуемому формату (пример: `И.О. Фамилия автора`, а не `ФИО автора`). Имя поля в коде (`fio`) не менять.
5. **Тесты и сборка:**
    При любых изменениях всегда проверять:
    ```bash
    pytest -v                  # All tests must pass
    cd frontend && npm run build # Build without TypeScript or Vite errors
    ```
