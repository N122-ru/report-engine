# Статус автономного релиза

## Подготовка версии 0.3.0

В текущем checkout `VERSION`, `frontend/package.json` и
`frontend/package-lock.json` согласованы на `0.3.0`. Это подготовка релиза,
а не утверждение о публикации: тег `v0.3.0` не создавался и будет поставлен
сопровождающим отдельно после проверки release-коммита.

Версия повышена до 0.3.0, поскольку добавлены новые возможности:

- MCP-контракт получил единый `snapshot_id`, идемпотентные операции и ссылки
  между вызовами пакетной команды.
- Добавлены слоистые инструкции и onboarding для агента, версионирование
  ресурсов и read-only проверка состояния отчёта.
- Усилены серверные проверки безопасности: изменения требуют актуальных
  ревизий, экспорт защищён проверкой состояния lint, а файловые источники
  изображений ограничены разрешённым корнем.

### Breaking changes

- `export_report` теперь требует предшествующего успешного `lint_report` после
  каждого изменения отчёта, реквизитов или изображений.
- Файловые источники в web доступны только при заданном
  `REPORT_ENGINE_MCP_FILE_ROOT`; без этой переменной web не принимает
  `file_path`.

## Подготовка версии 0.2.0

В текущем checkout `VERSION`, `frontend/package.json` и `frontend/package-lock.json`
согласованы на `0.2.0`. Это подготовка релиза, а не утверждение о публикации:
тег `v0.2.0` в рамках подготовки не создаётся. Сопровождающий отдельно публикует тег
по [процедуре релиза](release_tools/README.md#maintainer-release-procedure).

Версия повышена до 0.2.0, поскольку добавлены новые возможности, а не только
исправления:

- MCP-команда `batch` выполняет несколько команд последовательно за один вызов.
- Изображения можно передавать агенту через `file_path`, а не только в base64.
- Предпросмотр A4 учитывает переносы текста в таблицах и продолжает длинные
  абзацы на следующей странице без повторной красной строки.

Workflow релиза создаёт четыре ZIP-архива: headless и web для Linux x64
(runner Ubuntu 22.04) и Windows x64 (runner Windows Server 2022). В пакеты
включены Python и зависимости, поэтому установленные Python/Node.js не нужны.
Офисные конвертеры и системные шрифты не включаются.

## Подтверждённые результаты

- Регрессионный набор backend: пройдено 285 тестов командой `python -m pytest -v`
  в изолированном окружении с зависимостями из файлов проекта. Покрыты HTTP/live
  MCP, ядро состояния headless, `batch`, загрузка изображений через `file_path`,
  профили, ревизии, генерация документов, резервный сценарий PDF и loopback-защита.
- Frontend: пройдены 53 теста сервисов, включая 10 проверок пагинации A4;
  сборка TypeScript/Vite и lint завершены без ошибок. Сохраняются 30 существующих
  предупреждений lint и предупреждение сборки о размере chunk. Визуальная
  браузерная проверка исправленной пагинации не выполнялась.
- [CI на коммите `d0ca71e`](https://github.com/N122-ru/report-engine/actions/runs/38480672299)
  завершён успешно: установка зависимостей, сборка frontend, lint и backend-тесты.
  Этот результат относится к исходному коду до повышения версии; workflow CI
  не запускает `npm test`, поэтому 53 frontend-теста подтверждены локально.
- [Тестовая Docker-сборка через `workflow_dispatch`](https://github.com/N122-ru/report-engine/actions/runs/38479792449)
  на коммите `2643a80` завершена успешно: образ собран, контейнер запущен,
  `/api/health` и `/api/version` ответили успешно, архив сохранён как workflow artifact.
  Проверка выполнена с `VERSION=0.1.0`, до исправления пагинации A4 и подготовки
  0.2.0; это не проверка Docker-образа окончательного релизного коммита 0.2.0.
  Smoke не проверял экспорт DOCX/PDF, шрифты или содержимое ответа version API.
- Регрессионные проверки упаковки отклоняют отсутствующие или повреждённые
  frozen-ресурсы и web-ассеты. Исправление DOCX включает шаблоны и исходные
  каталоги, поэтому `docx/parts/../templates` разрешается в frozen-процессе.
  Обязательные данные проверяются побайтово относительно входов сборки.
- При предыдущей подготовке оба native-продукта для Linux прошли smoke-проверки
  экспорта вне checkout:
  initialize/create/export для headless MCP и HTTP-генерацию DOCX для web,
  включая нативные формулы и встроенный логотип. Smoke-поток также проверяет
  health, capabilities, SPA/ассеты web и целостность DOCX-архива с отключённым PDF.
- Runtime-проверки Linux launchers охватывают чистый MCP stdout, коды ошибок,
  открытие браузера после готовности и выбранные порты. Проверки Windows
  launchers, выполненные в Linux, являются статическими и проверяют UTF-8, пути,
  паузу при ошибке и команды браузера.

Это зафиксированные результаты подготовки, а не новая сертификация на чистой
машине. Workflow тега выполняет сборку frontend и pytest для всех четырёх
элементов matrix, проверяет равенство тега и `VERSION`, запускает каждый frozen-
исполняемый файл с `--help` и прикрепляет ZIP к GitHub Release. Его smoke-шаг
исполняемых файлов **не** проверяет экспорт DOCX из пакета; полная smoke-проверка
экспорта остаётся отдельной проверкой.

## Ещё не проверено

- Новые native-пакеты и полный frozen-smoke именно версии 0.2.0. В текущем
  окружении PyInstaller отсутствует; результаты предыдущей Linux-проверки
  не заменяют проверку новых архивов.
- Docker-сборка и smoke окончательного релизного коммита 0.2.0. Docker CLI
  в текущем окружении отсутствует; выше зафиксирован отдельный успешный запуск
  workflow на более раннем коммите.
- Полный runtime Windows: фактический запуск launchers, запуск браузера, MCP
  stdio/SSE, экспорт DOCX и пути на целевых установках Windows.
- Конвертация и отображение PDF на целевых машинах с их офисным CLI и шрифтами.
  Проверка версии не подтверждает успешную конвертацию или точность вёрстки.
- Эвристики антивируса/SmartScreen для распространяемых исполняемых файлов;
  статические проверки launchers и успешный экспорт в Linux не предсказывают
  эти результаты.

## Контракт PDF для релиза

DOCX остаётся доступным без конвертера. PDF включается только после успешной
локальной проверки версии `soffice`/`libreoffice` или `docbuilder`, если только
не отключён конфигурацией. Native-пакеты не скачивают конвертеры и не
устанавливают шрифты. Пользователи без этой возможности экспортируют DOCX и
преобразуют его вручную в Microsoft Office, LibreOffice или OnlyOffice.
Установленные в Docker конвертер и шрифты относятся к отдельному контракту
развёртывания и не входят в native-архивы.
