# Статус автономного релиза

## Подготовка версии 0.1.0

Реализация и подготовка релиза 0.1.0 завершены. Это не утверждение о том, что
версия 0.1.0 уже помечена тегом или опубликована: в текущем checkout значение
`VERSION` равно `0.1.0`. Сопровождающий должен опубликовать соответствующий тег
по [процедуре релиза](release_tools/README.md#maintainer-release-procedure).

Workflow релиза создаёт четыре ZIP-архива: headless и web для Linux x64
(runner Ubuntu 22.04) и Windows x64 (runner Windows Server 2022). В пакеты
включены Python и зависимости, поэтому установленные Python/Node.js не нужны.
Офисные конвертеры и системные шрифты не включаются.

## Подтверждённые результаты

- Регрессионный набор backend: 238 тестов пройдено в предыдущей проверке и при
  повторном sanity-запуске только для документации командой
  `backend/venv/bin/python3 -m pytest -v`. Покрыты HTTP/live MCP, ядро состояния
  headless, профили, ревизии, генерация документов, резервный сценарий PDF и
  loopback-защита автономного режима.
- Frontend: пройдены 43 теста сервисов, сборка TypeScript/Vite и lint; в
  предыдущей проверке зафиксировано 30 существующих предупреждений. Повторная
  сборка только для документации также пройдена с существующим предупреждением
  о размере chunk.
- Регрессионные проверки упаковки отклоняют отсутствующие или повреждённые
  frozen-ресурсы и web-ассеты. Исправление DOCX включает шаблоны и исходные
  каталоги, поэтому `docx/parts/../templates` разрешается в frozen-процессе.
  Обязательные данные проверяются побайтово относительно входов сборки.
- Оба native-продукта для Linux прошли smoke-проверки экспорта вне checkout:
  initialize/create/export для headless MCP и HTTP-генерацию DOCX для web,
  включая нативные формулы и встроенный логотип. Smoke-поток также проверяет
  health, capabilities, SPA/ассеты web и целостность DOCX-архива с отключённым PDF.
- Runtime-проверки Linux launchers охватывают чистый MCP stdout, коды ошибок,
  открытие браузера после готовности и выбранные порты. Проверки Windows
  launchers, выполненные в Linux, являются статическими и проверяют UTF-8, пути,
  паузу при ошибке и команды браузера.

Это зафиксированные результаты подготовки, а не новая сертификация на чистой
машине. Workflow тега выполняет сборку frontend и pytest для всех четырёх
элементов matrix, проверяет равенство тега и `VERSION`, запускает каждый frozen-
исполняемый файл с `--help` и прикрепляет ZIP к GitHub Release. Его smoke-шаг
исполняемых файлов **не** проверяет экспорт DOCX из пакета; полная smoke-проверка
экспорта остаётся отдельной проверкой.

## Ещё не проверено

- Полный runtime Windows: фактический запуск launchers, запуск браузера, MCP
  stdio/SSE, экспорт DOCX и пути на целевых установках Windows.
- Конвертация и отображение PDF на целевых машинах с их офисным CLI и шрифтами.
  Проверка версии не подтверждает успешную конвертацию или точность вёрстки.
- Эвристики антивируса/SmartScreen для распространяемых исполняемых файлов;
  статические проверки launchers и успешный экспорт в Linux не предсказывают
  эти результаты.

## Контракт PDF для релиза

DOCX остаётся доступным без конвертера. PDF включается только после успешной
локальной проверки версии `soffice`/`libreoffice` или `docbuilder`, если только
не отключён конфигурацией. Native-пакеты не скачивают конвертеры и не
устанавливают шрифты. Пользователи без этой возможности экспортируют DOCX и
преобразуют его вручную в Microsoft Office, LibreOffice или OnlyOffice.
Установленные в Docker конвертер и шрифты относятся к отдельному контракту
развёртывания и не входят в native-архивы.
